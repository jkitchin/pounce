POUNCE: an AI-first, pure-Rust interior-point optimizer for nonlinear, convex and complementarity-constrained problems

7 November 2026

Summary

Many problems in engineering and science are optimization problems: choose the operating conditions of a chemical plant, fit a model to data, or set the power flows on a grid, subject to physical laws written as equations and limits written as inequalities. POUNCE solves such problems. Its core is a port of Ipopt (Wächter and Biegler 2006), the interior-point solver most widely used for large, sparse, smooth nonlinear programs. Around that core it adds engines for convex quadratic and conic programs, active-set QP and SQP, parametric sensitivity (Pirnay et al. 2012), multistart searches for several local minima, and problems with complementarity constraints (MPCCs), in which one of two quantities must be zero at every pair.

POUNCE is written entirely in Rust, including its default sparse symmetric-indefinite linear solver, FERAL. It has no Fortran, BLAS or HSL dependency, so it builds from cargo, installs from pip on Linux, macOS and Windows, and runs in a web browser through WebAssembly and Pyodide. It reads AMPL .nl files and is available from Python (a scipy.optimize.minimize-compatible API and a Problem API), Pyomo (Bynum et al. 2021), CasADi (Andersson et al. 2019), Julia through JuMP and MathOptInterface (Lubin et al. 2023; Legat et al. 2022), GAMS, a C API, and a container image.

POUNCE was built AI-first. The human authors set the scope, the architecture and the standards of evidence. Most of the code, tests and documentation were written by an AI coding agent working under those standards. We describe that process, and how its output was checked, in AI usage disclosure.

Statement of need

Ipopt is the default local NLP solver in most algebraic modeling systems. Using it well has a practical cost. Good performance needs a licensed HSL linear solver (Duff 2004) or a separately built MUMPS (Amestoy et al. 2001), and the Fortran and C++ toolchain makes it hard to ship in a Python wheel or a browser. Teaching, web demonstrations, and research codes that people install with a single pip install all run into this cost. POUNCE removes it. It keeps Ipopt’s algorithm, option names and console output, so existing models, option files and experience carry over unchanged.

The second need is for solver features that are usually separate programs. POUNCE routes each model to the most specialized engine it supports. A convex QP goes to a homogeneous self-dual interior point (Ye et al. 1994), a general NLP to the Ipopt port, and a model with declared complementarity pairs to a driver that runs Scholtes regularization (Scholtes 2001) and an exact product formulation, then certifies the answer as strongly or weakly stationary. Sensitivity of the solution to parameters, a multistart search for distinct local minima, and a machine-readable JSON solve report are built in, not add-ons.

The intended users are researchers and students in process systems engineering, power systems and optimal control. They write models in Pyomo, CasADi, JuMP or AMPL and need a solver that installs anywhere and explains its answers.

State of the field

Ipopt (Wächter and Biegler 2006) is the reference implementation that POUNCE follows. MadNLP (Shin et al. 2024) is a Julia interior-point solver that targets GPUs and condensed-space methods. Uno (Vanaret and Montoison 2026) is a composable C++ framework that can reproduce several existing solver designs. Clarabel (Goulart and Chen 2024) is a Rust conic solver for convex problems only. None of these is a dependency-free, drop-in replacement for Ipopt that can also be shipped to WebAssembly.

The choice between building and contributing was made in favour of a port. The goal was Ipopt’s behaviour without its toolchain. That cannot be added to Ipopt itself, and it is a different goal from MadNLP’s or Uno’s. The port follows upstream closely enough to compare iterate by iterate. Where POUNCE departs from upstream, it does so behind an option whose documented value restores upstream behaviour. Examples are the cap on slack-row perturbations and the bound on tiny-step dual stalls.

Software design

POUNCE is a Cargo workspace of 25 crates. They separate the parts a reviewer would want to check on their own: the NLP algorithm (pounce-algorithm, pounce-nlp, pounce-restoration), linear algebra and linear solvers (pounce-linalg, pounce-linsol, pounce-feral, optional pounce-hsl), the convex and active-set engines (pounce-convex, pounce-qp), presolve, sensitivity, multistart, the .nl reader, and the front ends (CLI, Python, C, WebAssembly).

Three design decisions follow from the research setting.

  1. Upstream parity is the default. The port keeps Ipopt’s data flow and option semantics. A fix that changes the trajectory is measured against upstream and against the previous release before it merges.
  2. One entry point, routing to many engines. At the default solver_selection=auto, POUNCE classifies each model and sends it to the most specialized engine available. Every report records which engine answered, so a routing change shows up in the record even when the status and objective do not move.
  3. Answers carry their own evidence. Each solve can emit a versioned JSON report. It contains residuals, the iterations spent in every re-solve and fallback, and, for complementarity models, the stationarity certificate and how complementary the returned point is. A companion tool, pounce-studio, diagnoses a solve from that report.

Research impact statement

POUNCE has been public since May 2026 and has had 15 releases. pounce-solver has been downloaded about 42,600 times from PyPI since its first release on 25 May 2026, excluding mirrors (about 55,000 including them). pyomo-pounce has been downloaded about 14,500 times. Hans Mittelmann’s public benchmark of AMPL NLP solvers includes POUNCE (Mittelmann, n.d.).

POUNCE is in research use outside its authors’ group:

  • Opyrability, a process-operability package (Alves et al. 2024), uses POUNCE as its default solver.
  • SiNDAE, which trains neural differential-algebraic equations by the simultaneous approach (Lueg et al. 2025), runs its whole pipeline on POUNCE.
  • oximo, a Rust algebraic modeling library, has a POUNCE backend, and tellegen runs live interactive power-flow analysis on it.
  • The Julia interface was contributed by power-systems researchers and is validated against an optimal power flow adapter.

On the release benchmark (1,345 problems from the CUTE/Vanderbei AMPL collection, Mittelmann’s NLP set, Maros–Mészáros QPs (Maros and Mészáros 1999), LP collections, and application suites), POUNCE solves 1,309 to strict optimality, against 1,260 for Ipopt 3.14 with MA57 under the same 300 s limit. On MacMPEC, it reaches the best known objective on 158 of 178 problems and leaves none unsolved. Performance profiles (Dolan and Moré 2002) and the full per-problem tables are in the repository.

AI usage disclosure

POUNCE was developed with Anthropic’s Claude, through the Claude Code agent. Of the 3,711 commits on the main branch at version 0.16.0, 2,712 (73%) are authored or co-authored by Claude. AI-written work includes the Rust port, tests, benchmark harnesses, documentation, notebooks and a first draft of this paper. The human authors decided what to build, chose the architecture (a faithful port first, extensions behind options, engine routing, the evidence-carrying report) and set how correctness is shown. Every change was reviewed by a human before it merged.

The verification regime is designed for code that is cheap to produce and easy to get subtly wrong:

  • Changes are checked against independent oracles, not only against tests written alongside them: upstream Ipopt’s iterates, published best-known objectives, MILP-certified global optima, and recomputed KKT and complementarity residuals.
  • Any change that can alter the solver’s path is run through a fixture sweep on two Hessian modes and two CPU architectures, and every moved line must be explained before merge. The sweep exists because a regression that keeps the right answer but takes nearly four times the iterations passed a status-and-objective test suite and shipped.
  • Defects that tests missed are written up as post-mortems in dev-notes/ and distilled into the agent’s standing instructions (CLAUDE.md), so later work inherits them.
  • An adversarial test harness poses problems with known solutions to every engine and reports wrong answers.

The authors take full responsibility for the software and this paper.
