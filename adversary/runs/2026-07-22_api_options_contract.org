** (c) Out-of-range values — TWO DEFECTS

*** F1. Silent int32 truncation of integer options (=pounce.minimize= only)

| Input                       | int32 wrap | Result                                        |
|-----------------------------+------------+-----------------------------------------------|
| =max_iter=3=                | —          | nit=3, f=16.97674722 (reference)              |
| =max_iter=2**32+3= (4294967299) | 3      | *NO ERROR*, nit=3, f=16.97674722              |
| =max_iter=2**32+1=          | 1          | *NO ERROR*, nit=1, f=16.96877086              |
| =max_iter=2**33+7=          | 7          | *NO ERROR*, nit=7, f=17.01431805              |
| =max_iter=2**32=            | 0          | *NO ERROR*, nit=0, f=16.10969292              |
| =max_iter=10**12=           | −727379968 | rejected, but message quotes =max_iter=-727379968= |

The same values through the other surfaces:

| Surface | =max_iter=4294967299=                                                   |
|---------+-------------------------------------------------------------------------|
| CLI     | rc=2 — "Integer value expected, but non-integer option value ... found." |
| Pyomo   | rc=2 — same rejection                                                   |
| Python  | *silently applied as 3*                                                 |

Root cause is an unchecked cast in the PyO3 binding,
=crates/pounce-py/src/problem.rs:179=:

#+begin_src rust
if let Ok(i) = value.extract::<i64>() {
    self.int_opts.push((name.to_string(), i as Index));   // Index = i32: `as` truncates
    return Ok(());
}
#+end_src

=i as Index= is a wrapping conversion in Rust. Every integer-typed option set
through =Problem.add_option= (and therefore =pounce.minimize=) inherits this.
The failure is silent: no exception, no warning, and the solve returns a
plausible =OptimizeResult= — just one whose iteration budget is a number the
user never supplied. The =max_iter=10**12= case shows the same truncation
leaking into a diagnostic, which reports a negative limit the caller never typed.

* Cross-check / Verification

- F1 is confirmed behaviorally (=nit= exactly equals the int32-wrapped value for
  four independent inputs, matching the =max_iter=3= reference run to the last
  digit of the objective) and by source inspection of the unchecked =as= cast at
  =crates/pounce-py/src/problem.rs:179=. Not a formulation artifact: the CLI and
  Pyomo reject the identical option string.
- F2 is confirmed by the returned residual dictionary itself
  (=kkt_error=1.0= alongside =status='optimal'=) and by the known closed-form
  optimum \(x^*=(1,1)\), \(f^*=-1\), which the same call reproduces exactly at
  any sane =tol=. Reproduced identically on =solve_socp=.
- No pounce source was modified. Scripts:
  =adversary/runs/2026-07-22_api_options_contract.py= (probes a–e) and
  =adversary/runs/2026-07-22_api_options_followup.py= (F1/F2 isolation).

* Verdict

*SOLVER_BUG* — for F1. =pounce.minimize= silently substitutes a different value
for any integer option exceeding 2^31: =max_iter=2**32+3= is applied as
=max_iter=3=, the solve stops after three iterations at a non-optimal point, and
nothing — no exception, no warning, no field of the result — records that the
caller's request was altered. The CLI and the Pyomo plugin reject the same input,
so this is also a cross-surface contract violation, exactly the class of silent
option mishandling gh #213 / PR #214 set out to close, one layer lower in the
PyO3 binding. The fix is a checked conversion (=i32::try_from(i)=) in place of
the =as= cast.

Secondary, *SOLVER_LIMITATION* — for F2. =solve_qp= and =solve_socp= validate
=tol= not at all, while every other pounce surface rejects the same values.
=tol<=0= and =tol=nan= silently burn the full 199-iteration budget on a problem
that solves in one iteration; =tol=1e300= / =inf= return =status="optimal"= at
\(x=0\) for a problem whose optimum is \((1,1)\), with =kkt_error=1.0= in the
residuals it hands back, and that mislabel propagates up to
=minimize(solver_selection="qp-ipm")= as =success=True=.

Dimensions (a), (b) and (d) — unknown-key rejection, option efficacy, and type
errors — pass cleanly and are notably well hardened.
