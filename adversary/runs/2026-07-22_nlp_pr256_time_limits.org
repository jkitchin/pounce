** Latent risk (code-read; NOT reproduced empirically)

~predict_factor_overshoot~ fires *while still under budget* -- that is its
entire purpose. It aborts by returning ~false~ from ~solve_once~ /
~compute_search_direction~. But the caller's abort handler in
~crates/pounce-algorithm/src/ipopt_alg.rs:1370~ is:

: if let Some(ret) = self.deadline_status() { return IterateOutcome::Terminate(ret); }
: if !ok { ... return self.invoke_restoration_debugged(); /* or ErrorInStepComputation */ }

~deadline_status()~ is ~Deadline::exceeded()~, which by construction returns
~None~ at the moment the predictive guard fires. So a guard-triggered abort
should fall through to the ~!ok~ branch and be treated as a *step-computation
failure* -- routed into restoration, or, absent restoration, terminating as
~ErrorInStepComputation~ (AMPL band *500*, "failure"). The same structure
applies at ~ipopt_alg.rs:1618~, ~:1738~ and ~:2041~, all of which key off
~deadline_status()~.

I could not make this manifest. In every case where the guard demonstrably
fired (see Hypothesis E), the reactive ~deadline_exceeded~ check had already
tripped by the time control returned, so the correct 400 status was
produced anyway. The narrow window that would expose it -- a factorization
costing between ~50% and ~95% of the budget, so the guard arms *and* fires
before the clock crosses -- was not reachable with the fixtures available
here. Recording it as a latent correctness risk, not a demonstrated bug.

Verdict: *PASS* (empirically clean; one latent code path flagged).

* Hypothesis D -- feral_static_pivoting :: PASS

** Is it actually plumbed, or silently ignored?

*Plumbed.* ~camshape_6400~ gives a numerically *different* answer with static
pivoting on, which is only possible if ~with_static_pivoting~ really reaches
the factorization:

| route                                    | objective          | iters | n_factors |
|------------------------------------------+--------------------+-------+-----------|
| unset                                    | -4.4483776974779   |    87 |        88 |
| ~feral_static_pivoting yes~               | -4.44837769756148  |    87 |        88 |
| ~feral_static_pivoting no~                | -4.4483776974779   |    87 |        88 |
| ~POUNCE_FERAL_STATIC_PIVOTING=1~          | -4.44837769756148  |    87 |        88 |
| ~POUNCE_FERAL_STATIC_PIVOTING=0~          | -4.4483776974779   |    87 |        88 |
| ~POUNCE_FERAL_STATIC_PIVOTING=bogus~      | -4.4483776974779   |    87 |        88 |

Relative difference on/off: *1.9e-11*. The tri-state discipline is exactly
as documented: ~no~ / ~0~ / an unrecognised token all reproduce the unset
default bit-for-bit; only an explicit affirmative changes the numeric path.

** Is it answer-neutral?

Yes, to at least 10 significant figures on every well-posed problem tested:

| problem       | unset        | yes          | no           | status (all three) |
|---------------+--------------+--------------+--------------+--------------------|
| bratu         | 0            | 0            | 0            | SolveSucceeded     |
| camshape_6400 | -4.448377697 | -4.448377698 | -4.448377697 | SolveSucceeded     |
| cont5_2_4_l   | 0.0663713083 | 0.0663713083 | 0.0663713083 | SolveSucceeded     |
| clnlbeam      | 344.8761314  | 344.8761314  | 344.8761314  | SolveSucceeded     |

clnlbeam's 344.8761314 matches Ipopt exactly under all three settings.

** Cost

Static pivoting is *not* free on these problems -- it is a pessimization:

| problem       | unset (s) | yes (s) | no (s) | yes vs unset |
|---------------+-----------+---------+--------+--------------|
| bratu         |     0.069 |   0.075 |  0.064 |        +9%   |
| camshape_6400 |     2.212 |   2.253 |  2.154 |        +2%   |
| cont5_2_4_l   |    11.637 |  11.469 |  9.575 |        -1%   |
| clnlbeam      |    36.231 |  53.784 | 38.604 |       *+48%* |

clnlbeam takes 48% longer with static pivoting on, for an identical answer.
This vindicates the PR's design decision to keep the knob explicit, opt-in,
default-off, and deliberately *not* coupled to ~max_wall_time~. None of these
problems is in feral#8's delayed-pivot-cascade regime, so the intended
speedup could not be reproduced here (no emfl050 fixture is available in
this repo).

Verdict: *PASS*.

available in this repository the overshoot is dominated by the *first*

cancellation hook. The regime the guard actually helps (several
large factorizations inside one budget, e.g. discopt's per-node budgets)
is not represented here.

Verdict: *SOLVER_LIMITATION* -- not a bug; a correctly-scoped partial fix
whose benefit is unobservable on the available fixtures.
