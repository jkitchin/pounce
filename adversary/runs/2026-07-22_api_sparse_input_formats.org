#+TITLE: Adversary Run: Sparse Matrix Input & Structure Handling (solve_qp)
#+DATE: <2026-07-22>

* Problem
:PROPERTIES:
:FAMILY: api (qp entry point)
:CLASS: input-format / sparse-structure edge cases
:DIMENSION: API contracts, option handling, input edge cases
:SOURCE: closed-form KKT of a strictly convex equality-constrained QP (self-derived, confirmed in exact rationals with sympy) + cvxpy/CLARABEL
:KNOWN_OPTIMAL: -2.4179104477611940 (obj), x* = [0.089552238806, 0.238805970149, 0.417910447761, 0.253731343284]
:N_VARIABLES: 4
:N_CONSTRAINTS: 1 equality, 2 inequalities (both inactive)
:END:

\[
\min_{x\in\mathbb{R}^4}\ \tfrac12 x^\top P x + c^\top x
\quad\text{s.t.}\quad \mathbf{1}^\top x = 1,\quad x_0 \le 0.8,\ -x_3 \le 0.5
\]
\[
P=\begin{pmatrix}4&1&0&0\\1&3&1&0\\0&1&2&1\\0&0&1&5\end{pmatrix},\qquad
c=(-1,-2,-3,-4)^\top
\]

$P \succ 0$ and both inequalities are strictly inactive at the optimum
($Gx^\star - h = (-0.8896, -0.9179)$), so the optimum is the exact solution of
the KKT system $\begin{pmatrix}P & A^\top\\ A & 0\end{pmatrix}\begin{pmatrix}x\\y\end{pmatrix}
= \begin{pmatrix}-c\\ b\end{pmatrix}$ — a closed-form oracle independent of any
solver. The sympy exact-rational solve agrees with the float64 solve to
1.1e-16, and cvxpy/CLARABEL agrees to 4.4e-16.

Every input variant below is the *same mathematical problem*, differing only in
how the matrices are handed to =solve_qp=.

All six formats are accepted and every one returns a *bit-identical* objective
to the dense baseline. =python/pounce/qp.py:207 _coo= normalizes any object with
a =.tocoo()= method, so format is genuinely irrelevant. Each matrix was also
tested sparse in isolation (P only / A only / G only) — identical.

** (b) Explicit stored zeros — PASS

P inflated from nnz=10 to nnz=14 with structural zeros at (0,2),(2,0),(0,3),(3,0);
G from nnz=2 to nnz=4. Both bit-identical to the baseline. Structural zeros are
passed through to the Rust side as 0.0-valued triplets and are numerically inert.

** (c) Duplicate COO entries at the same (i,j) — PASS (convention respected)

Entries split as 0.4+0.6 (P off-diagonal), 0.25+0.75 (A), 0.5+0.5 (G). All three
returned the correct answer to 4.5e-14, i.e. the solver **sums** duplicates, matching
the scipy/COO convention. This was independently confirmed by a stationarity test
(see the confirmation script): the returned point satisfies $\nabla f = 0$ for the
*summed* matrix to 3.1e-11 and misses by 4.2e-01 for the overwritten one.

** (d) Unsorted CSR indices — PASS  (highest-value sub-test)

Column indices reversed within every row (=has_sorted_indices=False=, densified
matrices verified equal). P, A, G individually and all three at once: all
optimal, obj err <= 1.5e-13, x inf err <= 4.5e-14. No sorted-index assumption is
violated — expected, since the Python layer converts to COO triplets and never
hands an index-pointer array to a C/Rust routine that could assume ordering.

** (e) Empty sparse matrices (nnz = 0) — PASS

| case                                  | status  | obj                      | err vs closed form |
|---------------------------------------+---------+--------------------------+--------------------|
| G = csr_matrix((0,4)), h = []          | optimal | -2.4179104477614426e+00  | 2.49e-13           |
| G = csr_matrix((2,4)) (all zeros)      | optimal | -2.4179104477616402e+00  | 4.46e-13           |
| P = csr_matrix((4,4)) → LP             | optimal | -4.0000000000005356e+00  | 5.36e-13           |
| P = zeros((4,4)) dense → LP            | optimal | -4.0000000000005356e+00  | 5.36e-13           |
| P = None → LP                          | optimal | -4.0000000000005356e+00  | 5.36e-13           |

An all-zero sparse P is treated exactly like =P=None= (an LP), bit-identically;
the LP closed form (min $c^\top x$ on the unit simplex = $-4$) is matched.
A 0-row G with an empty h is accepted rather than erroring.

** (f) Triangle convention for P — documented, followed, but silent when violated

Documented in two places, consistently:
- =docs/src/convex-solver.md:59= — "``P`` (lower triangle used, assumed symmetric)"
- =python/pounce/qp.py:456= (=solve_qp= docstring) — "``P`` (lower triangle is used; assumed symmetric)"

Implementation =_lower_triangle_coo= (=python/pounce/qp.py:233=) keeps entries with
=row >= col= and discards the rest.

| P storage                | status  | obj                      | x inf err |
|--------------------------+---------+--------------------------+-----------|
| full symmetric           | optimal | -2.4179104477613436e+00  |  4.47e-14 |
| lower triangle only      | optimal | -2.4179104477613436e+00  |  4.47e-14 |
| upper triangle only      | optimal | -2.7272727272740216e+00  |  9.23e-02 |

Full and lower-only agree bit-for-bit — the documented convention is correctly
implemented, and there is **no** silent halving/doubling of the Hessian. Passing
the *upper* triangle only silently drops every off-diagonal and the solver sees
=diag(4,3,2,5)=; the predicted objective for that diagonal-only Hessian is
-2.7272727272727266, matching the returned -2.7272727272740216. This is the
documented contract being applied to an input that violates its "assumed
symmetric" precondition, so it is **not** a bug — but it is silent, and no
check could plausibly catch it (an upper-triangular P is a perfectly legal
asymmetric matrix whose lower triangle is diagonal).

** (c2) FINDING — check_psd guard is bypassed by duplicate COO entries

While probing (c) I found that the issue-#112 PSD guard and the solver disagree
about what the matrix *is*.

=python/pounce/qp.py:255= =_min_eig_lower_coo= reconstructs the Hessian with
**assignment**:

#+begin_src python
    for ri, ci, vi in zip(pr, pc, pv):
        M[ri, ci] = vi          # <-- last duplicate wins; should be +=
        M[ci, ri] = vi
#+end_src

whereas the solver **accumulates** duplicates (confirmed in (c)). For a P built
as a COO with duplicate entries the guard therefore checks a different matrix
than the one that is solved.

Trap instance (n=2, box $[-10,10]^2$, $c=(-1,-1)$):

#+begin_src python
P = sp.coo_matrix(([2.0, 2.0, 1.5, 1.5], ([0,1,1,1],[0,1,0,0])), shape=(2,2))
#+end_src

- Solver's matrix (duplicates summed): =[[2,3],[3,2]]=, eigenvalues =[-1, 5]= — **indefinite**.
- Guard's matrix (duplicates overwritten): =[[2,1.5],[1.5,2]]=, eigenvalues =[0.5, 3.5]= — PD, guard passes.

| input for the SAME matrix                    | outcome                                                      |
|----------------------------------------------+--------------------------------------------------------------|
| dense =np.array([[2,3],[3,2]])=              | correctly REJECTED: "P is not positive semidefinite (min eigenvalue -1.000e+00)" |
| duplicate-COO (identical math)               | ACCEPTED, =status="optimal"=, =obj=-2.000000e-01=, =x=[0.2,0.2]= |
| duplicate-COO with =check_psd=True=          | STILL ACCEPTED, same wrong answer                            |

The returned point is a **saddle**, not a minimum. The true minimum over the box
is $-100$ at $x=(10,-10)$ — confirmed by three independent oracles (corner
enumeration of the indefinite QP, a 401x401 dense grid, and scipy L-BFGS-B). The
reported objective overstates the true minimum by 99.8, with
=status="optimal"= and no warning. This is precisely the silently-wrong
=optimal= that issue #112 added the guard to prevent; the guard simply has a
hole for duplicate-entry COO input.

Passing =check_psd=True= does not help, because the bug is in the guard's own
matrix reconstruction.

* Cross-check / Verification
- **Primary oracle — dense equivalent.** Every accepted sparse variant in (a)–(e)
  and the lower-triangle case in (f) matched the dense baseline objective
  *bit-for-bit* (identical float64 repr), far beyond the 1e-9 requirement of (g).
- **Closed form.** float64 KKT solve agrees with sympy's exact-rational solve to
  1.1e-16; all obj errors <= 5.4e-13, all x inf errors <= 1.1e-13.
- **cvxpy/CLARABEL.** obj = -2.4179104477611943e+00, |Δobj| vs closed form = 4.4e-16.
- **Finding (c2) confirmed by:** (i) the dense equivalent of the same matrix being
  *rejected* by the very same guard; (ii) a stationarity test proving the solver
  used the summed (indefinite) matrix; (iii) corner enumeration, a 401x401 grid,
  and scipy L-BFGS-B all reaching -100 vs the reported -0.2.

* Verdict
=SOLVER_BUG= — narrowly, and *not* in the sparse handling itself. Sub-tests
(a)–(e) and (g) are clean: all six scipy formats, explicit stored zeros,
duplicate COO entries, unsorted CSR indices, and empty (nnz=0) matrices are all
accepted and every one reproduces the dense/closed-form answer bit-for-bit. The
two highest-value sub-tests both came back clean — unsorted CSR indices are
handled correctly (the Python layer goes through COO triplets, so no C-side
sorted-index assumption exists), and the lower-triangle Hessian convention is
documented in two places and implemented exactly as documented, with no silent
halving or doubling.

The one genuine defect is a *guard* inconsistency uncovered by sub-test (c):
=_min_eig_lower_coo= (=python/pounce/qp.py:255=) reconstructs the Hessian with
=M[ri,ci] = vi= instead of =+=', so for a duplicate-entry COO =P= the
=check_psd= guard validates a different matrix than the solver factorizes. An
indefinite Hessian then passes the guard and =solve_qp= returns
=status="optimal"= at a saddle point, objective -0.2 against a true minimum of
-100 — a silently wrong answer from an input format pounce accepts and otherwise
handles correctly. The one-character fix (=+== in both assignments) makes the
guard see exactly the matrix the solver sees.

Secondary (documented, not filed): an upper-triangle-only =P= is silently read
as diagonal-only. Correct per the documented "lower triangle used, assumed
symmetric" contract, but worth a mention in the docs as the most likely way a
user silently loses their off-diagonals.
