** The contract ba6d5b3 states

From the commit message and PR #270:

#+begin_quote
Rank by (feasible_enough, objective): a point inside the feasibility band beats
one outside it outright, objective decides only among points already inside the
band, and the band is capped at the upstream-default acceptable_constr_viol_tol
(1e-2) *so a user-widened value cannot admit gross infeasibility*.
#+end_quote

** The ranking as implemented

#+begin_src rust
let feasible = |v: Number| v.is_finite() && v <= band;   // band = min(acv_tol, 1e-2)
let (a_ok, b_ok) = (feasible(a_viol), feasible(b_viol));
if a_ok != b_ok { return a_ok; }
a_obj < b_obj                       // <-- both outside the band lands here
#+end_src

The cap makes =feasible_enough= a *predicate*, not an ordering. It separates
"inside 1e-2" from "outside 1e-2" and nothing else. Once **both** the incumbent
and the recorded candidate sit outside the cap, =a_ok == b_ok == false=, the
feasibility term drops out entirely and the rule reverts to =a_obj < b_obj= --
bit-for-bit the pre-fix rule that #267 was filed against. The fix protects a
feasible incumbent; it does not bound the trade among infeasible ones.

The commit's own unit test asserts this branch as intended behaviour:

#+begin_src rust
// Both infeasible: still ranked by objective (no feasible point to
// protect), so the fallback never *gains* infeasibility for free here.
assert!(ranks_better_within_band(-2.0, 5.0, -1.0, 9.0, band));
#+end_src

The comment does not follow from the code. That case improves feasibility
(5.0 < 9.0) only by coincidence of the chosen numbers; the branch it exercises
ignores =a_viol= and =b_viol= completely, so it equally admits 9.0 replacing 5.0.
The run below is that admitted case, live.

** Scope, stated fairly

- *Config-gated.* =dual_diverging_streak= is 0 (off) by default; the trap needs
  it on plus a loosened acceptable band. Real-world default-path exposure: none.
- *Milder trigger than #267.* This needs =acceptable_constr_viol_tol=1e0=, a
  decade tighter than the =1e1= #267 required -- so ba6d5b3 raised the bar but
  did not remove it.
- *Guard-off control is also verify-rejected* here (viol 3.228e-4 at feas-tol
  1e-6), so this is not a feasible-to-infeasible flip. The finding is the
  *3000x feasibility degradation* the fallback chose, and the fact that it made
  feasibility strictly worse than the incumbent it replaced.
- *Broader sweep.* 13 CLI fixtures x streak {1,2,15} x acv {1e1,1e0,1e-1} x
  max_iter {10,20,30,50,200} x {loose, default} tolerances produced 33
  guard-attributable feasibility regressions. deb7 at streak=2 / acv=1e0 is the
  largest and cleanest; a second at acv=1e1 / max_iter=20 shows the same trade
  (viol 3.680e0 incumbent discarded for viol 4.933e0 at a lower objective).
- *No default-path finding.* As with #267, at stock tolerances the sweep found
  no feasibility regression attributable to the fallback.

* Verdict

*SOLVER_BUG* (incomplete fix of gh #267) -- ba6d5b3's =(feasible_enough,
objective)= key is a two-class partition, not an ordering, so it constrains the
fallback only while one of the two points is inside =FEASIBLE_ENOUGH_CAP=1e-2=.
Above the cap the feasibility term vanishes and the ranking reverts exactly to
the pre-fix =a_obj < b_obj=, which is the rule #267 was filed against. On deb7
with =dual_diverging_streak=2= and a one-decade-widened acceptable band, the
post-fix fallback discards an incumbent at viol 5.292e-1 in favour of a recorded
point at viol 9.951e-1 to gain 36 % of objective, and returns it under
=solve_result_num = 100=; =pounce verify= rejects it (exit 20) and its objective
sits 41.7 % below Ipopt's feasible local optimum. The commit's specific claim
that "a user-widened value cannot admit gross infeasibility" does not hold, and
the unit test comment asserting the both-infeasible branch "never *gains*
infeasibility for free" is contradicted by the branch's own code, which reads
neither violation. Behaviour at and below the cap is correct and #270's headline
autocorr_bern55-06 result reproduces; the no-regression property on converging
solves holds. The natural repair is to make the key an ordering rather than a
partition -- e.g. rank on =(min(viol, band), obj)= or require
=a_viol <= b_viol= before letting objective decide among infeasible points --
so the fallback can never return a point less feasible than the one it replaces.
