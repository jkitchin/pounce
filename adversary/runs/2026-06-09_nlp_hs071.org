* Cross-check / Verification
Ipopt (via Pyomo) solves the identical model to the same optimum; the published
HS071 optimum agrees to ~1e-9. The objective and all four coordinates match
Ipopt to 1e-8. The point is therefore optimal beyond doubt — the disagreement is
purely in the *reported* =success= flag, not the numerical answer.

Probing the reporting across conditions:

| Start / options        | info.status | status name                   | success | rel err  |

| (1,5,5,1), nlp, default | 3          | Search_Direction_Too_Small    | False   | 8.57e-10 |

Two intertwined facets:
1. The Python facade maps =success= as =int(info["status"]) == 0= only
   (python/pounce/_minimize.py:448), so status 1 = Solved_To_Acceptable_Level →
   =success=False=. This contradicts pounce's *own* differentiable path, whose
   =_OK_STATUS = ("Solve_Succeeded", "Solved_To_Acceptable_Level")=, and the
   scipy/Ipopt convention where acceptable-level is a success.
2. On the documented default start the NLP solver terminates with status 3 at a
   KKT-optimal point where Ipopt returns Solve_Succeeded.

Net effect: the canonical Ipopt tutorial problem, run from its documented start,
reports failure despite converging to the verified optimum.

* Verdict
SOLVER_LIMITATION (reporting) — the answer is correct and oracle-confirmed, but
=success=False= is returned at a verified optimum, both because
Solved_To_Acceptable_Level is excluded from the success mapping and because the
default-start solve halts on Search_Direction_Becomes_Too_Small where Ipopt
succeeds. Filed as a GitHub issue (reporting/UX defect, not a wrong answer).
